## R2 真实品牌受控试点协议

### 一、目的与边界

R2 用 3–5 个可删除的真实案例验证诊断工作流是否可执行，重点验证实体识别、行业因素覆盖、消费者 App 采集、重复性表达和下游交接

R2 不用于证明评分权重、阈值、等级或平台总体表现，真实案例产物只能放在 Git 忽略的 `work/` 目录

### 二、案例组合

案例组合必须共同覆盖：

- 高决策成本 B2B
- 消费品牌
- 区域服务
- 本地中小或微型企业
- 品牌、公司、门店、产品线或关联主体存在实体复杂性

单个案例可以覆盖多个类别，但不得把任一案例的行业字段、品牌名称或经验判断写入通用 Schema 和合成示例

### 三、冻结条件

采集前必须冻结：

1. `ResearchScope`、`DomainContext` 和 `QueryProtocol`
2. `BrandEntityProfile`、`IndustryProfile`、`MeasurementPlan` 和 `ContentFoundationProtocol`
3. 至少一条高商业价值关键查询
4. 消费者产品、模式、搜索要求、地域状态、重复次数和时间窗
5. 标注者、实体复核者和行业因素复核者

地区敏感案例必须把地域写入冻结查询，不能依赖未记录的账号或设备位置

### 四、采集协议

消费者 App 浏览器是 R2 主证据，官方 API 与公开网页只能作为独立辅助通道

- 同一冻结查询至少重复 2 次，推荐 3 次
- 每次保留独立 `PlatformRequest`、`RawPlatformResponse` 和截图
- 搜索是必要条件时，必须由页面中的显式搜索状态或来源面板证明实际执行
- App 与 API 不混合聚合，API 未证明联网时不得替代消费者 App 搜索
- 登录、账号、验证码、OAuth 和权限开通始终由用户本人完成

### 五、实体复核

每次回答必须使用以下互斥状态之一：

| 状态 | 含义 |
|---|---|
| `exact_canonical` | 出现已核验的规范名称 |
| `verified_alias` | 出现已核验别名 |
| `verified_related_entity` | 出现已核验关联产品、门店或主体，仍与品牌层分开统计 |
| `other_entity_only` | 只出现同品类其他实体，未证明与目标相关 |
| `ambiguous` | 文本可能命中，但身份关系不足以确认 |
| `absent` | 未出现规范名或已核验匹配项 |
| `unreviewed` | 尚未完成人工复核 |

名称相似、同一行业、同一地点或模型自身陈述都不足以建立实体关系

### 六、稳定性结果

`repeated_experiment.py` 输出以下描述性指标：

- 搜索执行率
- 独立回答率和回答长度变异系数
- 提及实体与推荐实体的平均两两 Jaccard
- 首个实体一致率
- 可获得时的引用 URL Jaccard

这些指标只描述重复运行稳定性，不是 GEO 得分，也不判断事实正确性

### 七、诊断交接

每个完成案例必须生成 `DiagnosticHandoff`，按以下链条组织：

```text
实体复核结果
  -> 已观察事实、推断、未知与反证
  -> 业务影响
  -> 证据缺口
  -> 待规划问题
  -> 验证指标
```

交接包不得包含执行动作或把低置信度假设改写为事实，规划角色负责后续优先级和行动选择

### 八、完成门槛

R2 只有同时满足以下条件才可标记 `completed`：

- 3–5 个案例覆盖全部五类组合
- 每个案例的研究包和诊断包通过校验
- 每个案例达到冻结的消费者 App 重复次数
- 原始请求、回答和截图通过采集契约校验
- 重复实验通过校验并产出稳定性结果
- 实体与行业因素完成至少单标注者复核
- 每个案例形成通过校验的诊断交接包
- `pilot_validate.py` 返回 `assessment=completed`

R2 完成仍不证明多标注者一致性、WorkBuddy 运行时绑定、权重科学性或跨平台总体有效性，这些分别属于 R3、产品集成和后续校准阶段
