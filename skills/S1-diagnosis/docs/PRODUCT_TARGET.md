## Brand GEO Audit 在 WorkBuddy 中的诊断专家目标

### 一、短期目标

`brand-geo-audit` 的短期产品目标，是作为 WorkBuddy GEO 专业团中的诊断专家，对品牌在生成式 AI 答案和公开内容供给中的当前状态进行证据化诊断，并把可追溯的问题清单交给下游规划角色

它不是完整品牌营销顾问，也不负责直接修改官网、发布内容、投放广告或承诺 GEO 结果

记忆锚点：诊断负责认清问题，规划负责选择行动，执行负责改变外部世界

### 二、角色边界

诊断专家负责：

- 确认研究对象、业务边界和品牌实体
- 建立与业务问题相关的查询协议
- 采集或接收消费者 AI 产品、官方 API 和公开内容证据
- 区分事实、推断、未知、缺失和反证
- 输出分项观测、证据缺口、稳定性限制和待验证问题
- 向规划专家交付结构化诊断结果

诊断专家不负责：

- 把单次回答解释为稳定平台结论
- 把 API 结果解释为消费者 App 等价结果
- 在证据不足时生成正式总分、等级或改进承诺
- 用某个行业或某个真实品牌测试案例定义通用架构
- 代表用户完成登录、授权、账号选择或权限开通
- 未经用户授权修改外部网站、账号、内容或业务系统

### 三、输入

最低输入：

- 品牌或待确认的品牌名称
- 目标市场和语言
- 业务领域或待调查的业务边界
- 至少一个目标受众

正式诊断还需要：

- 品牌实体和官方渠道证据
- 行业决策因素或其待确认清单
- 竞品或替代方案
- 冻结的查询集
- 目标平台、通道、模式和采集时间

输入不足时，产出应是研究缺口和下一步取证要求，而不是评分

### 四、默认产出

WorkBuddy 首个 MVP 的默认产出模式为 `diagnostic`，产品界面采用“结论优先、证据下沉”

它应包含：

1. 观测范围和计划完成度
2. 分平台、分业务查询族的稳定可见、稳定缺席和问法敏感结论
3. 影响结论成立的关键证据缺口
4. 可展开的测试问题与审计明细
5. 给规划专家的机器可读汇总

默认不以单一总分或字母等级代替诊断证据

### 五、报告模式

| 模式 | 用途 | 总分与等级 |
|---|---|---|
| `exploratory` | 输入不足时的范围澄清和方向摸底 | 不显示 |
| `diagnostic` | WorkBuddy 默认诊断交付 | 不显示正式总分，可展示分项和样本 |
| `experimental_score` | 内部研究、回归和校准 | 可显示，但必须标记实验性 |
| `validated_score` | 外部验证后的保留模式 | 当前不可用 |

R1 已实现 `exploratory`、`diagnostic` 和 `experimental_score` 的报告投影，`validated_score` 仍不可用；完整探索式研究运行时仍属后续能力

### 六、下游交接

诊断专家向规划专家交付的不是自由文本建议，而是以下结构：

```text
已观察事实
  -> 证据与反证
  -> 业务影响
  -> 未确认原因假设
  -> 待规划问题
  -> 建议验证指标
```

规划专家可以选择行动优先级和解决路径，但不得把诊断中的低置信度假设改写为事实

### 七、MVP 发布门槛

- 当前实现、候选架构和长期路线在文档中明确分离
- 真实品牌测试案例可以删除，不影响 Skill、示例和测试
- 每项诊断结论可以追溯到来源或观测
- 内容基础已调查，或明确标记为未完成
- 不同平台、模型、模式和通道不混合解释
- 报告默认不发布未经校准的正式等级
- 下游规划角色能够识别事实、假设、缺口和可行动问题

### 八、当前状态

当前模块已经具备 v2 研究、证据、评分、质量审计、建议校验和 HTML 报告链路，以及 R1 运行清单、品牌实体、行业适配、测量计划、内容基础协议和报告模式

R2 已增加受控试点、消费者 App 重复观测、实体复核状态、描述性稳定性和独立下游交接包

查询族汇总和精简客户报告已经进入 MVP；WorkBuddy 单专家适配已完成仓库化、官方校验、本地注册和可见浏览器链路验收，当前运行时绑定状态为 `verified`

该状态只证明单专家能够从源码构建并调用浏览器运行时，不证明完整真实诊断、专家团交接或测量方法已经外部验证

多标注者可靠性、多行业校准和外部验证仍属后续能力，实施顺序见 [ROADMAP.md](ROADMAP.md)
